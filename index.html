JAMS

Judge-gated Agentic Middleware Search

让 agent 从空白写出 LLM→Jev 中间层，再用没见过的场景和模型检验它

把一个指令模型接到 Jev 决策 API 上，要写一层"中间层"：把请求变成 prompt，再把模型输出变成每道题的概率分布。JAMS 让代码 agent 直接改写这一整层，每份代码先过 judge 和人工复核，再按准确率与用时选优。搜索只用 Qwen3.5-4B / 9B 和 6 个训练场景，得到的代码冻结后，原样跑在另外 6 个测试场景、5 个模型上。

02

我们怎么做的

JAMS 是一个 GEPA 式的进化搜索，只是被改写的不再是一段提示词，而是整份 middleware.py。每一轮由代码 agent 读训练小批上的反馈，写出一份新的中间层；judge 判它有没有走捷径，通过的才去跑 validation；最后在准确率和用时的 Pareto 前沿上选父候选，进入下一轮。

STEP 1

抽训练小批

从 6 个训练场景里随机挑 3 个，抽 128 个 case 作为本轮反馈。

STEP 2

代码 agent 改写

Claude Code（DeepSeek-V4.1-Flash 驱动），每轮全新 session。可以在小批上调用真实模型自测。

STEP 3 · GATE

Judge agent 审代码

glm-5.3-flash 驱动，只看代码和规则，用 mock 模型跑扰动探针。判 fail 就打回重写，最多 3 次。

STEP 4

完整 validation

6 个训练场景的 validation 全部跑完，记录准确率和秒/题。

STEP 5

Pareto 选父

在 {准确率, 用时} 的前沿上挑下一轮的父候选。

↺ 回到 STEP 1，30 轮（Qwen3.5-9B 跑满 30 轮，Qwen3.5-4B 按人工决定在第 24 轮截断），单 seed第 1 轮没有父候选，从空白开始

02 · B

为了不 hack，我们做了什么

让 agent 直接写代码，最大的风险是它会写出只对评测集有效的捷径：认出数据集、硬编码规则、让模型走个过场。我们的前一版实验就出现过这种情况，提升里有很大一部分来自这类捷径。所以 JAMS 的大部分设计都花在堵这些路上。下面 10 条按作用分三组。

不让它看到测试

搜索过程拿不到任何测试场景的信息，也认不出题目来自哪个数据集。

01
按场景切分，而不是按样本切分

12 个场景分成两组，互不重叠。搜索只用 6 个训练场景，测试用另外 6 个，测试数据在搜索期间根本不挂载到容器里。这样测出的是"换一个全新任务还能不能用"，而不是同一个数据集的另一批样本。

0个场景同时出现在搜索和测试里

02
从空白开始，不给种子

第 1 轮没有父候选，agent 只拿到接口说明和训练小批，连 LLM2Jev 的做法都不给。LLM2Jev 只在最后当对照。

0行初始代码

03
反馈去掉来源

agent 看到的训练反馈里删掉了 source 字段，case_id 也换成不透明编号。它不知道某道题来自哪个数据集，也就没法写"如果是 BANKING77 就怎样"。

source字段删除，编号不透明

不让它走捷径

写清楚什么不许做，再用 agent 和人两道关去查。

04
10 条写死的禁止项

每轮的任务说明里都写明：答案必须来自模型自己的输出，中间层只能按题型和选项数这类结构分支。

  1. 绕过模型直接出答案
  2. 按内容分支
  3. 领域词表
  4. 领域化 prompt
  5. 记忆训练样本
  6. 表面启发式
  7. 结构指纹
  8. 规则做决定、模型走过场
  9. 跨请求传递信息
  10. 绕过 harness 限制

10条规则，任何一条不过即拒

05
Judge 是一个会动手的 agent

judge 不只读代码：它用 mock 模型在虚构请求上跑候选，再改字段名、换说法、打乱选项顺序，看调用结构会不会跟着内容变。判不准（uncertain）也按 fail 处理。它看不到任何数据、分数，也看不到写代码 agent 的过程记录。

3种扰动探针；uncertain = fail

06
Judge 先校准，再冻结

正式搜索前，拿前一版实验的 26 份 hack 候选和 3 份手写的通用实现去测 judge。26 份必须全判 fail，3 份必须全判 pass，达标后冻结 prompt、rubric 和 hash，搜索中途不再改。

26/26 · 3/3hack 全拦下，通用实现全放行

07
最终候选逐条人工复核

选出来的每份代码都按 10 条规则对着行号复核，搜索过程中也抽查逐轮候选。例如 4B 搜索第 17 轮的一份候选被查出：模型输出无法解析时固定返回 0.55，而不是中性的 0.5。这类候选不会被选作最终版本。

11份逐轮人工审阅记录

让对比公平

现成方法不是抄论文里的数字，而是放进同一个框架里重新跑。

08
冻结代码，换模型直接跑

只在 Qwen3.5-4B / 9B 上搜索。代码冻结后，原样跑到 Qwen3-8B、Qwen3-4B-Instruct 和 gemma-4-E4B 上，不针对新模型做任何调整；跨系列的 gemma 也一样。

3个模型从没参与过搜索

09
现成方法放进同一接口

5 个现成方法都移植成同一个 decide(request, llm)，共用同一个模型服务和计时方式。jev-local 需要 prompt logprob，我们单独为它打开了这个权限，JAMS 没有。AnyJev 默认用跨请求的 batch 先验，这违反 JAMS 自己也要遵守的第 9 条，所以换成上游提供的 content_free 先验。

同一服务 · 同一权重 · 同一计时

10
标准先写定，区间一起报

"比 LLM2Jev 好"的判断标准在搜索开始前写进 issue。每个比较都报告整 case 配对 bootstrap 的 95% 区间；超时补跑对所有方法一视同仁。

02 · C

agent 写出了什么

四份代码都没有任何场景相关的分支，靠的是几种通用做法：把选项编成字母放进同一页，读一次下一个 token 的概率；长列表先粗筛再复评；用多种选项顺序抵消位置偏置。下面是 judge 和人工复核记录里写的机制。

JAMS-9BG_iso · 搜索于 Qwen3.5-9B

  • 字母页 + 一次读分布：选项编成 A、B、C… 放进一页，读一次下一个 token 的概率，得到全部选项的分布。
  • 顺序平均：同一页按不同选项顺序各打一次再取平均，抵消模型偏爱某个位置的倾向。
  • 短名单复评：长列表先整页粗筛，再把前几名放到一张短页上重打。
page = "A. …\nB. …\nC. …\nAnswer:"
p = mean(score(page, order)
         for order in orders)
top = shortlist(p) → rescore(top)

JAMS-4BG_iso · 搜索于 Qwen3.5-4B

  • 三路信号：先让模型贪心生成它认为最好的选项；再读单符号编号的分布作为粗分布；最后对最有希望的 12 个选项聚焦复评。
  • 对数线性校准：模型自己点名的选项在 log 空间加权，并保留 1% 残差给全部选项，结果仍是合法分布。
  • 大选项集分批召回，调用数有上限。
pick   = generate(prompt)
coarse = score(all options)
focus  = score(top-12 ∪ {pick})
p = calibrate(focus, pick)
    + 0.01 · coarse

JAMS-4B-fastG_fast · 搜索于 Qwen3.5-4B

  • 单 token 编号打分：一次前向读出所有编号的概率。
  • 分块锦标赛：选项多时分块打分，再对胜出者聚焦复评。
  • Noul 题读 true / false 两极的 token 概率并做单调校准；出错时回退到 0.5。
for chunk in chunks(options):
    keep += top_k(score(chunk))
p = score(keep)          # 聚焦复评
noul = mono(P(true))

JAMS-9B-fastG_fast · 搜索于 Qwen3.5-9B

  • 正反两序打分：字母页按正序和倒序各读一次分布再合并；选项多于字母表时，改让模型生成选项文本。
  • 粗分布 + 短名单：先得到全体粗分布，按分数取短名单聚焦复评，并给全部选项留一小部分残差概率。
  • Noul 题读 yes / no 的 token 概率并做单调校准。
p = mean(score(page),
         score(reversed(page)))
top = shortlist(p) → rescore(top)
p = mix(p_top, p, residual)

02 · D

对比的现成方法

这些方法都来自已发表的论文、开源仓库或推理框架自带的接口，没有我们自己发明的基线。

LLM2Jev
每个选项单独问一次 yes/no，再归一化，N 个选项调用 N 次。也是搜索时的对照基线 M₀。
SGLang decisions
SGLang 自带的 /v1/decisions：选项编成字母放进同一个 prompt，读一次字母概率；超过 26 个选项用 AA、AB 这样的双字母。
AnyJev（L0）
选项轮换 K 次后取平均，再除掉标签先验。先验用 content_free 模式估计，不跨请求。最多支持 26 个选项。
Chat 直接生成
来自 LLM-as-Jev 的生成模式：选项编号，让模型通过 chat 接口贪心生成编号，答案取 one-hot。
jev-local
每个选项单独算一次文本的平均 logprob，除以温度后做 softmax。默认不套 chat template。
